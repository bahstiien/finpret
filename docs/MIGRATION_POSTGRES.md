# Migration Supabase → PostgreSQL (VPS)

Branche `postgres`, partie de `main` (8c2a795). Décisions : Postgres sur le VPS Hostinger, Better Auth à la place de Supabase Auth.

## Inventaire de départ

| Brique Supabase | Usage dans le code | Remplacement |
| --- | --- | --- |
| Auth | OTP e-mail, Google OAuth, MFA TOTP, admin (lister, supprimer) | Better Auth : plugins `emailOTP`, `twoFactor`, `admin`, fournisseur Google ; e-mails envoyés par Resend (déjà configuré) |
| Postgres + RLS | 21 migrations, 113 politiques, `auth.uid()` ×46, `auth.users` ×25, rôles `authenticated` ×146 / `anon` ×2 / `service_role` ×1 | Même Postgres. RLS conservée grâce à une couche de compatibilité (voir plus bas) |
| PostgREST (`supabase-js`) | ~330 appels `.from()`, 20 `.rpc()`, dans ~77 fichiers | Kysely sur `pg`, types générés depuis la base (`kysely-codegen`) |
| Realtime | courses et session (`ShoppingScreen`, `SessionProvider`), 5 tables publiées | Triggers `NOTIFY` + route SSE `/api/realtime` |
| Storage | 2 buckets privés de PDF, lus et écrits seulement par le serveur | Volume Docker monté sur le VPS (`/data/files`), sauvegardé avec la base |
| CLI (`db push`, `db:types`, `test db`) | scripts `supabase-remote.mjs`, `env:supabase` | `scripts/migrate.mjs` (table `schema_migrations`), `kysely-codegen`, tests PGlite existants |

## Principe : garder la RLS telle quelle

Plutôt que réécrire 113 politiques, la migration de compatibilité `20261018000000_compat.sql`, jouée en premier, recrée ce que Supabase fournissait :

- le schéma `extensions` (pgcrypto) et le `search_path` de la base ;
- les rôles `anon`, `authenticated`, `service_role` (NOLOGIN, `service_role` avec `BYPASSRLS`) et leurs droits par défaut ;
- le schéma `auth` : table `auth.users` (colonnes Better Auth + colonnes héritées de Supabase), et `auth.uid()` qui lit `request.jwt.claims`, comme sous Supabase : les tests pgTAP n'ont pas changé.

L'app se connecte avec un rôle de connexion sans privilège, membre des trois rôles (`grant anon, authenticated, service_role to <rôle>`). Chaque connexion du pool démarre en `anon`. `src/server/db.ts` ouvre une transaction et pose `request.jwt.claims` + `role` en local :

- `withUser(userId, db => …)` : rôle `authenticated`, la RLS s'applique ;
- `withAnon(db => …)` : rôle `anon` ;
- `withAdmin(db => …)` : rôle `service_role` (remplace la clé de service).

Les tables de sessions, de comptes OAuth et de TOTP de Better Auth arrivent en phase 2.

## Conventions de la phase 3 (supabase-js → Kysely)

- **Ouvrir la base** : `createClient()` (session) → `withSession((db) => …)` de `@/server/session` ; `createAdminClient()` → `withAdmin((db) => …)` de `@/server/db` ; utilisateur déjà connu → `withUser(user.id, (db) => …)`. Une fonction qui recevait un client en paramètre reçoit `db: Db` (`import type { Db } from "@/server/db"`). Garder les appels réseau (Stripe, e-mails, LLM) hors de la transaction quand c'est simple.
- **Types** : `@/server/db.types` remplace `@/lib/supabase/database.types` (`Json`, `HouseholdRole`, `AssociationRole`…). Les formats renvoyés ne changent pas : dates et horodatages en texte ISO, `numeric`/`bigint` en nombres.
- **Lectures** : `.single()` → `executeTakeFirstOrThrow()` ; `.maybeSingle()` → `executeTakeFirst()` (`undefined`, pas `null`) ; liste → `execute()`. `.order(c, { ascending: false })` → `.orderBy(c, "desc")` ; `.in(c, [])` vide → ne pas lancer la requête (Kysely refuse `in ()`). Comptage `{ count: "exact", head: true }` → `select((eb) => eb.fn.countAll<number>().as("n"))`. Relations embarquées (`households(id, name)`) → `innerJoin`/`leftJoin`. Filtre JSON `props->>key` → `sql\`props->>'key'\``.
- **Écritures** : `insert(...).select()` → `insertInto(...).values(...).returning([...])` ; `upsert(row, { onConflict: "a,b" })` → `onConflict((oc) => oc.columns(["a", "b"]).doUpdateSet(...))`. Toute valeur **jsonb** passe par `json(value)` de `@/server/db` (un tableau JS deviendrait un tableau Postgres). Les colonnes `text[]`/`int[]` reçoivent un tableau JS tel quel.
- **Fonctions SQL** : `supabase.rpc("f", args)` → `rpc<T>(db, "f", args)` (valeur : uuid, boolean, jsonb, void) ou `rpcRows<T>(db, "f", args)` (`returns table`, `setof`, type composite).
- **Erreurs** : supabase-js renvoyait `{ data, error }`, `pg` lève une exception. `if (error) return { ok: false, error: toUserMessage(error) }` → `try { … } catch (e) { return { ok: false, error: toUserMessage(e) }; }`. Une mise à jour ou suppression filtrée par la RLS ne lève rien : vérifier le nombre de lignes (`numUpdatedRows`, `numDeletedRows`, ou `returning`) là où le code vérifiait `data.length`.
- **Storage** (`.storage.from(...)`) : inchangé jusqu'à la phase 5, via `createAdminClient()`.
- Référence : `src/server/session.ts` et `src/server/household-context.ts`.

## Phases

Chaque phase laisse l'app fonctionnelle et testée (`pnpm test`, `pnpm test:db:lite`, `pnpm typecheck`).

1. **Socle base** ✅ — migration de compatibilité, `pnpm db:migrate` (table `schema_migrations`), `pnpm db:local start|stop|status|reset` (cluster dans `.pgdata/`, port 54329, binaires PostgreSQL pour Windows, sans Docker), `pnpm db:types:pg` (génère `src/server/db.types.ts`), `src/server/db.ts`. Vérifié : 21 migrations sur PostgreSQL 18 (rejouables), `test:db:lite` vert, typecheck et lint propres ; RLS contrôlée sur PG 18 avec un rôle de connexion non superutilisateur (A voit son foyer, B rien, `anon` refusé, `service_role` voit tout, connexion hors transaction refusée).
2. **Auth** ✅ — Better Auth 1.7.10 (`src/server/auth.ts`, route `/api/auth/[...all]`) : lien magique (15 min, jeton haché, e-mail `MagicLinkEmail` via Resend, affiché dans le terminal sans Resend en dev), Google, Apple derrière `FEATURES.appleSignIn`, liaison des comptes de même adresse, événement `signup` à la création. Middleware : contrôle optimiste du cookie, session vérifiée en base par `requireUser`. Second facteur du back-office maison (`src/server/totp.ts` testé sur les vecteurs RFC 6238, `src/server/mfa.ts`) : le plugin `twoFactor` de Better Auth ne couvre que la connexion par mot de passe. `auth.admin.*` remplacé par `src/server/users.ts`. Vérifié en local : connexion par lien magique de bout en bout, profil créé par le trigger, lien rejoué refusé, redirection des pages protégées, suppression en cascade. **Pas vérifié** : Google (identifiants à créer), saisie TOTP (le contrôle `is_admin` passe encore par Supabase). L'app n'est utilisable de bout en bout qu'après la phase 3 : les requêtes de données passent encore par Supabase.
3. **Accès aux données** ✅ — les 344 appels `.from()` / `.rpc()` de 74 fichiers sont en Kysely (conventions ci-dessus). Le pool renvoie les mêmes formats que PostgREST, horodatages à la microseconde compris (`updated_at` sert de version) ; base et connexions en UTC comme Supabase. Les types générés reprennent les unions de valeurs des colonnes bornées (`scripts/db-types-overrides.json`). Le navigateur n'écrit plus en base : l'écran des courses et la session de cuisine passent par des actions serveur (`shopping-sync.ts`, `session-sync.ts`). Tests serveur sur une vraie base PGlite (`tests/unit/pglite-db.ts`) au lieu du faux client Supabase ; e2e : liens magiques déposés dans un fichier (`E2E_MAGIC_LINK_DIR`, localhost seulement), données de test en SQL. Écarts assumés : une erreur de base ignorée par supabase-js fait désormais échouer la requête (sauf là où le code tolérait l'échec exprès) ; plusieurs suites d'écritures sont atomiques ; la clôture trimestrielle tient en une transaction et n'envoie les e-mails qu'après validation. Vérifié : typecheck, lint, 546 tests Vitest, pgTAP, et parcours local (connexion, onboarding, menu modifié, coche des courses, démarrage de session, réglages, découvrir). E2E (desktop, build de production, port 3300) : 27 réussis en parallèle ; les échecs restants en parallèle sont des dépassements de délai sous charge (repassés un à un : 14 réussis), plus le temps réel des courses (phase 4) et la case « Afficher la série et le passeport » que Playwright ne peut pas cliquer (libellé posé dessus, composant inchangé). `db.ts` signale toute transaction ouverte dans une autre (risque d'épuisement du pool) : aucune relevée. Better Auth lit l'IP client dans `X-Forwarded-For` (Caddy) ; son limiteur est coupé pour les e2e locaux. Seuls les appels Storage passent encore par Supabase (phase 5).
4. **Realtime** ✅ — migration `20261108000000_household_events.sql` : triggers `pg_notify('household_events', {t, h, w})` sur les 7 tables que publiait `supabase_realtime`, émis à la validation, sans données. `src/server/realtime.ts` : une connexion `LISTEN` par processus (reconnexion automatique), répartie par foyer. `/api/realtime?household=…` : flux SSE réservé aux membres du foyer (battement toutes les 25 s, événement `ready` à chaque (re)connexion). Côté navigateur, `useHouseholdEvents` (`src/lib/use-household-events.ts`) : les courses relisent la liste (regroupée sur 150 ms) et, avec les achats réels, rafraîchissent la page sur un achat ou un signalement ; la session suit l'état des autres appareils si `FEATURES.sharedSession` est activé. Caddy ne compresse plus `/api/realtime`. Vérifié : 3 tests PGlite (notification par changement, rien sur une transaction annulée, session), 549 tests Vitest, e2e « courses partagées » (coche visible chez l'autre compte en moins de 2 s, ajouts simultanés, hors ligne).
5. **Fichiers** ✅ — `src/server/files.ts` remplace Supabase Storage : fichiers sous `FILES_DIR` (`.data/files` en local), même découpage `<bucket>/<chemin>` que les anciens buckets (les `statement_path` en base restent valables), chemins contrôlés (aucune sortie du bucket), écriture via fichier temporaire. Fiche tuto (`kit.ts`), clôture trimestrielle (`closing.ts`), téléchargement des relevés (`/asso/releves/[id]/pdf`) et renvoi par le back-office branchés dessus ; `src/lib/supabase/` supprimé, plus aucun appel à Supabase dans `src/`. Vérifié : 11 tests (`tests/unit/files.test.ts`, dont les chemins refusés), 560 tests Vitest, et en local la fiche tuto générée puis relue depuis le disque (6,7 s puis 82 ms), le relevé téléchargé par la responsable, 404 pour un identifiant inconnu ou mal formé. **À faire en phase 6** : volume Docker monté sur `FILES_DIR` et inclus dans la sauvegarde ; **en phase 7** : rapatrier les PDF existants des buckets Supabase.
6. **Prod VPS** ✅ (préparée, pas encore déployée) — `deploy/docker-compose.yml` : service `db` (`postgres:18`, volume `pgdata`, port sur `127.0.0.1` du VPS seulement), service `migrate` (même image, `scripts/migrate.mjs` en propriétaire ; l'app ne démarre que s'il réussit), app connectée en `finpret_app` (rôle créé par `deploy/db-init/01-roles.sh`, ni superutilisateur ni propriétaire : la RLS s'applique), volume `files` sur `/data/files`. Mots de passe dans `~/finpret/.env` (`deploy/compose.env.example`) ; le déploiement n'y modifie plus que `APP_TAG` et revient en arrière si les migrations échouent. `deploy/backup.sh` : `pg_dump` vérifié + archive des fichiers chaque nuit, 14 jours sur le VPS, copie `rclone` hors serveur et signal de surveillance facultatifs. `docs/RESTAURATION.md` réécrit pour le VPS. CI : base `postgres:18` en conteneur de service, migrations, seed et e2e à chaque poussée (plus de secret Supabase). Dockerfile : migrations dans l'image, plus d'arguments Supabase. Vérifié sans Docker, sur PostgreSQL 18 local : rôles + migrations sur une base vierge, puis avec `finpret_app` (pas superutilisateur, aucune table possédée, Better Auth, RLS anon/authenticated, LISTEN, UTC), puis sauvegarde `pg_dump` → restauration selon `RESTAURATION.md` (mêmes décomptes, même dernière migration, 7 triggers, RLS conservée). **Pas vérifié** : la pile Docker elle-même (`docker compose up`, image, Caddy), la CI GitHub et le premier déploiement.
7. **Bascule des données** — export depuis Supabase (`public` + id/e-mail de `auth.users`), import, vérification des comptes. Les sessions en cours sont perdues (reconnexion par OTP) ; les secrets TOTP sont repris depuis `auth.mfa_factors` si l'export le permet, sinon réenrôlement.
8. **Nettoyage** — suppression de `@supabase/*`, `supabase/`, variables `SUPABASE_*`, mise à jour de `CLAUDE.md`, `SPEC.md` (stack), `README.md`.

## Points ouverts

- Les branches `design-v2-1`, `prise-en-main`, `progres` touchent les mêmes fichiers : à fusionner dans `main` avant la phase 3 pour limiter les conflits, ou à rebaser après.
- Données de production existantes sur Supabase : volume et comptes réels à confirmer avant la phase 7.
- Hors Docker en local : PostgreSQL 18 installé nativement sur Windows, cluster de dev lancé par `pnpm db:local start` ; PGlite reste l'outil des tests.
- E2E en parallèle sous Windows : plusieurs tests dépassent leur délai alors qu'ils passent un à un ; à revoir (nombre de workers, délais) indépendamment de la migration.
- `/settings/profile` : la case « Afficher la série et le passeport » est recouverte par son libellé pour Playwright (`locator.uncheck` échoue) ; le réglage fonctionne à la main.
- `src/app/app/session` : avertissement d'hydratation sur l'heure de fin prévue (calculée côté serveur puis côté navigateur, à cheval sur une minute). Antérieur à la migration.
